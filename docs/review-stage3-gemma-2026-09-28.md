## Comparison decision and known limits

The off/think pairing should use the same test IDs and procedural seeds, suite/checker, model file, backend/build, template hash, and quality context. The scoring code allows different per-item token budgets for generation-config comparisons; report those budgets and truncation counts because they can affect quality. A higher think score supports a choice only if the paired quality-difference interval excludes zero in think's favor and the latency policy is met. Overlapping intervals do not establish a thinking benefit.

**Static comparison gap:** `contractCheck` checks applied kwargs and runtime-accepted sampling only on the candidate `rows` (the think set). Its `base` rows are used for template/runtime/model identity uniformity but are not checked for their own kwargs or accepted sampling. Thus the current scorer can mark think comparable even when the off comparator lacks those proofs. The first-export audit must apply the full contract to both sets before accepting an off/think conclusion. Also, if GGUF template inspection does not detect `enable_thinking`, `templateKwargsFor` sends no toggle despite the explicit config IDs; verify model metadata plus actual requested/applied fields before treating the labels as different modes. The runtime may omit `generation_settings` or template hash; neither can be assumed from this read-only review.

The runtime's thought counter returns `reasoningTokens:null` when no thought delimiter is seen, while `runQuality` currently coerces that null to zero and labels `tokenSource:'runtime'`. Thus a measured zero in the export does not by itself prove a true zero reasoning-token count. Record this as token-split provenance uncertainty if it occurs; do not infer that thinking was absent or faster from that field alone. The insight text also labels the off config as T=0 even though this request sets T=1, so use the persisted request/rows for the baseline label.
