# GAPS REMAINING ranked

## G01 — HIGH: a confirmed recommendation can violate recorded safety and use estimated memory as measured

**Rules:** I-1.1/I-1.2/I-7.6. **Locations:** V:237,250,277; C:115,123,125; F:6; I:279.

**Executed failing scenario:** synthetic max_quality candidate, clean 8K, decode 40, measured Q80, estimated peak VRAM 8/16 GiB, shared usage unavailable, minimum RAM 3 GiB against recorded 4 GiB floor. `verdicts()` returned winner `a`, `confirmed:true`, memory score **100 with kind measured**, simultaneously emitting critical I-4.3. No safety gate failed. `val(metric,true)` means positive numeric value, **not measured provenance**. Missing spill becomes zero solely for the memory cap. A same-model unsafe full-offload candidate can consequently veto a safe partial one.

**Fix:** evaluate a measured safety verdict before ranking/vetoes; preserve each operand's provenance and make absent safety evidence not verified. Do not allow DECLARED decisive terms to confirm a pick.

## G02 — HIGH: renderer uses interp-1 meanings and skips reinterpretation of interp-1 records

**Rules:** I-7.2 and §10 historical display. **Locations:** P:13,20,96; ResultsPage.tsx:267; DashboardPage.tsx:34.

**Scenario:** ENGINE_RULES comes from `rules.v1.json`, so stored interp-1 equals the supposed current engine and returns before calling computeRecommendation. Conversely interp-2 is considered old. Hovering a new I-5.7 quarantine citation shows the old leaderboard rule; new I-1.2/I-7.2 meanings likewise mismatch. The engine JSON itself has correct IDs; the display does not.

**Fix:** load the active v2 catalog and resolve historical tooltips by the recommendation's recorded version; retain stored recommendations while showing a separately versioned reinterpretation.

**No rewrite found:** main/index.ts:191–202 reads sessionInputs and computes without saveRecommendation; S:79 inserts recommendations rather than rewriting them during display. ResultsPage.tsx:277 replaces insights only in an in-memory copy. However its own-workload reinterpretation keeps the old decision trace/reasons, so new insights may accompany an unrelated old decision and no new trace view. This needs explicit separation, not a database rewrite.

## G03 — HIGH: nominal “common rung” does not establish comparable measurements

**Rules:** I-7.1/I-1.2/I-6.0. **Locations:** V:197; C:43–46; I:331; V:155–164.

**Executed scenario:** candidate `short` has clean 4K and 16K rows at 100 t/s, candidate `exact` has 8K at 40 t/s. Max_quality selects `short`, sets scoringRung=8192, actually scores it at **4096**, and reports “candidates are compared at the common scoring rung 8K” without disclosing the substitution. Both are confirmed. Prompt occupancy, KV, template, gen config and quality ctx/budget are unchecked; stripping genId removes a useful consistency guard. Same testId/seed is necessary but insufficient to establish the guide's full comparison scope.

**Fix:** require a matching measured comparison basis or explicitly mark unmatched components/comparisons provisional; validate stored scope identities before paired comparisons. Never claim a common rung when using different rungs.

## G04 — HIGH: public recommend/verdicts request overrides are ignored numerically

**Rule:** I-1.1. **Locations:** V:174–178,254,261; N:45 and recommendForWorkload at end of file.

**Executed scenario:** `recommend([40-t/s candidate], machine, 'max_quality', undefined, [], {minDecodeTps:100})` returns a best candidate; the wrapper with the identical request returns no best. Direct verdicts has the same issue. Request values mark the floor as user-supplied but the number remains the profile's value. requiredContext has the analogous problem. Production wrapper/session code normally pre-applies the effective profile; the exported API itself does not.

**Fix:** apply effectiveProfile once inside the shared verdict entry point, then let wrappers delegate without relying on callers to pre-transform cfg.

## G05 — HIGH: decision trace can state the opposite of the actual tie-break

**Rule:** I-7.2. **Locations:** V:311–350,380–395; T:49; N's trace-chain reason rendering.

**Executed scenario:** six categories, ten unique items each; higherQ passes indices 0–7 and runs at 10 t/s; faster passes indices 2–8 and runs at 40 t/s. Paired difference faster−higherQ = **−10 [−24.55,+5.08]**, so quality is neutralized and faster wins with non-quality totals **30 vs 28.077**. Trace then says its deciding chain is original `total: faster 79 vs higherQ 84.076923, decided:true`. The visible chain cannot explain why the lower total won.

Trace also omits safety evaluation, per-component rung/provenance, recommendedCtx/reason, and actual norm/cliff config; excluded unusable candidates are absent from eligibleSet. Provisional counterfactual is prose, not an evaluated alternative ranking. Some reasons use trace, but N recomputes paired differences/attribution and I reads component state directly. Pairwise winner changes are bounded by n² iterations without a cycle verdict; do not present that bounded walk as a proven total ordering.

**Fix:** capture the actual comparisons and effective totals as they occur, including component basis, rejected candidates and policy parameters; render the decision explanation solely from those stored events. Detect/report comparison cycles explicitly.

## G06 — HIGH: persisted history is not supplied when generating the stored recommendation

## G07 — MED: memory/spill explanations still invent scope or mislabel algorithms
